# Notes, reminders, or to-do lists
Agora vamos fazer o caso de uso de adicionar notas, LEMBRETES E listas.

## Notas
As notas obrigatoriamente precisam ter conteúdo e o texto da nota em si. Pode ser que tenha um título, mas até então não sei como poderei separar título de descrição. Como inicialmente não quero usar nenhuma LLM para gerar um título, vamos deixar como tendo apenas: nota e data. A data é a data em que está sendo gerada a nota.

## Lembretes
Lembretes são um tipo de nota com alguma data definida, por exemplo: lembrar dia 10 que tenho uma consulta. É para que eu me lembre de alguma coisa em um período específico. 

Por enquanto, vamos apenas aceitar datas obrigatoriamente e horário como opcional. Deixe um todo dentro do caminho docs/todos.md para que futuramente consigamos implementar algo como datas relativas, por exemplo: daqui a 3 dias tenho uma consulta.

## Todo
Lista de tarefas sempre vem com 1 ou mais itens que precisam ser realizados; no banco também vamos adicionar uma coluna para dizer se foi feito ou não. Pode ter um título, mas, como não sei como separar isso do restante, prefiro que seja mantida somente a lista e a data que está sendo salva.

Futuramente, a lista de tarefas deverá aceitar uma data para ser atrelada, tipo o lembrete, como se fosse um deadline.

## Como será salvo no banco

Como todas são notas, acredito que podemos abstrair para apenas uma tabela no banco e usar outras para salvar itens que estejam relacionados, como os itens da lista de tarefas, ou usar um campo do tipo array para guardar os valores (o que for mais fácil para futuras pesquisas).

### Índices

Provavelmente irei precisar pesquisar no require e precisei dar uma filtrada nos dados, acho que pela data, por tarefas que não foram finalizadas ou por algum termo dentro do conteúdo das notas. 

## Execução

Vou implementar o caso de uso de notas/lembretes/todos como um novo serviço `NotesService` registrado no dispatcher para a categoria `notes`. A detecção do sub-tipo (nota vs lembrete vs todo) usa uma segunda chamada Jev com um template dedicado (`note.json`) com uma choice question `note_type`, chamada apenas para mensagens classificadas como notes. Lembretes têm data obrigatória e horário opcional, extraídos por um parser determinístico PT-BR (dd/mm[/aaaa], "dia N", hoje, amanhã; horário "14h"/"14:00"); se a data não for parseável, a resposta orienta o usuário. Todos são salvos como nota + itens em tabela separada (`todo_items`, com coluna done). O require busca por termo (LIKE no conteúdo), por data (incluindo "ontem") ou por tarefas não finalizadas, conforme o conteúdo da mensagem. Persistência em duas tabelas: `notes` (type, content, date, time) e `todo_items` (note_id, text, done, position). O harness de validação ganha o flow `note` e o `docs/todos.md` registra o futuro de datas relativas e deadlines. 

## Implementação

Implementado em 2026-09-30: `NotesService` registrado no dispatcher para a categoria `notes`. O sub-tipo é detectado por uma segunda chamada Jev (`pkg/jev/requests/note.json`, choice question `note_type` com critérios afiados: nota = sentença única sem data e sem estrutura de lista; lembrete = data específica obrigatória; todo = estrutura de lista com separadores ou marcadores). Lembretes extraem data (dd/mm[/aaaa], "dia N", hoje, amanhã, ontem) e horário opcional (14h, 14:00) via `DateParser` determinístico; data não parseável retorna orientação ao usuário. Todos são divididos em itens (`SplitTodoItems`: linhas → numeração → vírgulas/ponto-e-vírgula) e persistidos com a nota. Persistência em `notes` (type, content, date, time) + `todo_items` (note_id FK cascade, text, done, position), com `NotesRepository` (Create atômico, FindByDate, FindUnfinished, FindByTerm). O require filtra por data, tarefas não finalizadas ou termo no conteúdo (stopwords PT-BR). O harness ganhou o flow `note` (16 prompts de validação) e a UI renderiza os ramos de nota/lembrete/todo com badges e lista de itens. Limitações conhecidas registradas em `docs/todos.md`: rótulo inicial colado no primeiro item do todo, colisão "contém"/"ontem" no parser, e datas relativas/deadlines como trabalho futuro.
