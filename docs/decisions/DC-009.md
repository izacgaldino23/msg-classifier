\# Two Entries



Agora que temos um projeto mais completo, quero ter dois novos tipos de entrada e com saidas separadas. Hoje temos uma aplicação que retorna web, focando 100% web. O que eu quero fazer é ter uma api para quando quiser chamar, ter aquele padrão rest. E outra entrada para caso eu queira chamar via cli.



Por enquanto também quero manter o front. Talvez possamos ver uma melhor forma de reusar o que ja temos e somente adaptar. Então vamos pensar no seguinte:

* Primeiro vamos tornar as saidas usaveis para camadas diferentes (web, api e cli)
* Vamos começar a disponibilizar a api, e para documentação usar o swago.
* Por ultimo vamos criar um entrypoint para um cli interativo.



Devo poder iniciar cada um deles de forma separada. Para melhorar essa parte de desenvolvimento quero que usemos 3 branches diferentes uma para cada ponto acima. Vamos usar o github stack para empilhar esses prs. Assim vou conseguir dar uma revisada no código.



Para isso, vamos criar um pipe básico usando github actions (já na primeira branch, para as outras herdarem) que rode tests e build. Assim conseguimos ver se esta tudo ok. Pode commitar e ir dando push nas branches. O resultado deve ser três prs stacados criados no github.

## Como isso é executado

Três branches empilhadas, cada uma abrindo PR contra a anterior, para revisão separada.

**1. `feat/web-entry`** (base `main`) — sem mudança de comportamento. Apaga o `views.ResultData`, que é uma
cópia campo a campo do `UseCaseOutcome` (mesmos nomes de campo, então nenhum template muda). Extrai o
`internal/app` como raiz de composição única (`Classifier`, `Dispatcher`, `Data`, `Prompts`), o que tira as
~90 linhas de wiring duplicado que as três entradas teriam. O `BackfillNameNorm` passa a rodar uma vez por
processo — é idempotente. Renomeia `cmd/api` para `cmd/web`, porque o nome já estava errado: ele serve web.
O DSN ganha `busy_timeout(5000)` e `journal_mode(WAL)`, que é o que torna três escritores no mesmo arquivo
SQLite seguros; o `SetMaxOpenConns(1)` continua, porque é por processo. Entra o GitHub Actions com build,
vet e test. **A prova de que não houve mudança de comportamento é a suíte de testes atual passando sem
nenhuma edição.**

**2. `feat/rest-api`** (base `feat/web-entry`) — novo binário `cmd/api` na `:8081`. `POST /api/v1/messages`
roda o mesmo `Classify → Dispatch` e responde JSON. A consulta de dados é somente leitura via `DataService`,
que já existe. O apresentador JSON é um `switch` sobre `models.Action`, e o apresentador de erro reaproveita
as mesmas regras de status do web (400/502/500) no corpo `{"error":"..."}`. Sem endpoints de escrita: o
caminho de edição do `/data` é moldado por formulário HTML e não há lógica de negócio para reaproveitar.
Sem `/prompts`: é um harness de desenvolvedor que só usa checkbox. Documentado com swaggo.

**3. `feat/cli`** (base `feat/rest-api`) — `MoneyBRL` e `DateBR` saem de `views` e vão para `internal/ptbr`,
ao lado de `ParseAmount` e `ParseDate`, que leem de volta o que a UI renderiza. Os templates não mudam: eles
chamam os nomes do `FuncMap` (`money`, `dateBR`), não os símbolos Go. `Confidence`, `Deref`, `Label` e
`BadgeVariant` ficam em `views`, porque são apresentação de tela e o CLI não precisa deles. `internal/cli`
transforma o `UseCaseOutcome` em linhas de terminal reutilizando `ptbr`, e `cmd/cli` faz o REPL: prompt,
lê uma linha, classifica, despacha, imprime. Sai em `exit`, EOF ou Ctrl+C.

O `models.Action` não foi tocado. Ele afirma um fato (`contact_not_found`), e `{"action":"contact_not_found"}`
é um contrato de API perfectly válido — a decisão de tela mora em `result.html`, não no enum.

### O que foi entregue

`cmd/api` sobe em `API_PORT` (padrão 8081) e serve JSON. A tabela final de rotas:

| Método | Rota | Query |
| --- | --- | --- |
| `POST` | `/api/v1/messages` | corpo `message` |
| `GET` | `/api/v1/contacts` | `filter` |
| `GET` | `/api/v1/notes` | `filter` |
| `GET` | `/api/v1/transactions` | `filter`, `search` |

`action` é o discriminante da resposta e toda falha sai como `{"error": "..."}`. Sem endpoint de escrita e
sem `/prompts`: a consulta é somente leitura. O Swagger UI fica em `/swagger/index.html`, servido do pacote
gerado `docs/`.

### O que foi entregue — CLI

`cmd/cli` sobe um REPL: prompt `msg> `, lê uma linha, classifica e despacha pelo mesmo
núcleo de sempre e imprime o resultado em texto puro. `internal/cli` tem só duas
coisas — `Render`, que vira o `UseCaseOutcome` em linhas de terminal (o bloco de
classificação sai com as escolhas cruas, `contact/add`, e a extração marca cada
segmento com ✓/✗), e o loop de leitura, que para em `exit`, `sair`, `quit` ou EOF;
um erro no meio do caminho só imprime `erro: ...` e o loop segue, porque um tropeço
não deve matar a sessão.

`MoneyBRL` e `DateBR` mudaram para `internal/ptbr/format.go`, ao lado de
`ParseAmount`/`ParseDate` — o que a tela e o terminal imprimem é exatamente o que
os parsers relêem. Os templates não mudaram: continuam chamando os nomes do
`FuncMap` (`money`, `dateBR`), nunca os símbolos Go. `Confidence`, `Deref`, `Label`
e `BadgeVariant` ficaram em `views`, porque são apresentação de tela e o CLI não
precisa deles. O binário do CLI não carrega `html/template`: `internal/cli` não
importa `views` nem `api`.
