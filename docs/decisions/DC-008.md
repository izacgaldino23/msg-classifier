# Validation before adding new data to the database

Os tipos de dados que temos funcionando por agora são:
- Contato
- Notas
- Finanças

Pode ser que em algum momento o usuário tente adicionar algum dado que já está salvo, principalmente no caso de contatos e finanças. Para evitar duplicidade de dados, podemos implementar uma validação antes de adicionar novos dados ao banco de dados.

Acredito que para nome é mais fácil ja que temos menos campos para validar, mas para finanças pode ser mais complicado, pois o usuário pode adicionar uma transação que já existe, mas com um valor diferente ou em uma data diferente. Então precisamos pensar em como podemos validar esses dados antes de adicioná-los ao banco de dados.

Por isso essa tarefa é para pensar em como podemos validar os dados antes de adicioná-los ao banco de dados, para evitar duplicidade de dados e garantir que o usuário não adicione dados que já existem.

## Loop de interação com o usuário

Acredito que quando começarmos a pensar nessa caso talvez tenhamos que pedir alguma informação extra ao usuário ou até uma confirmação que ele quer atualizar ou adicionar um novo dado. Então precisamos pensar em como podemos fazer isso de forma amigável e intuitiva para o usuário, sem que ele se sinta perdido ou confuso.

Como agora temos 3 tipos de entrada, WEB, CLI e API, precisamos pensar em como podemos fazer isso de forma consistente em todas as interfaces, para que o usuário tenha a mesma experiência independente da interface que ele estiver usando. Ou pelos verificar qual delas é possivel fazer esse loop de interação com o usuário.

Enfim, o próximo tópico será preenchido com as ideias que eu tive para validar os dados antes de adicioná-los ao banco de dados. Se você tiver alguma ideia, por favor, adicione nesse tópico.

## Ideias para validação de dados

### 1. Escolher campos para validação

Cada categoria possui campos principais que podem ser usados para validar se o dado já existe ou não. Por exemplo, para contatos podemos usar o nome e o telefone, para notas podemos usar o título e a data, e para finanças podemos usar a descrição, o valor e a data.

Alguns dados podem simplemesnte não ter um campo que possa ser usado para validação. Nesse caso a gente pula direto para a adição do dado.

### 2. Loop de interação com o usuário

Esse loop vai ser usado inicialmente nesse caso, mas futuramente podemos usar ele para outras funcionalidades do bot. A ideia é que o bot pergunte ao usuário se ele quer atualizar o dado existente ou adicionar um novo dado, caso o dado já exista no banco de dados.

## Como esta tarefa será executada

A validação será feita na camada de serviço, antes de qualquer `Create`: cada fluxo
(contato, nota, finança) monta a chave de duplicado do seu formato e consulta o
banco; se existir e o usuário ainda não escolheu nada, nada é salvo — a tela/CLI
recebem um resultado "já existe" com três botões (atualizar / adicionar mesmo
assim / cancelar). A escolha volta na própria mensagem reenviada com um campo
`dup_action` (estado zero no servidor): `new` pula a checagem e insere, `update`
faz o merge dos campos preenchidos no registro existente (ID preservado). O WEB e
o CLI fazem o loop; a API só informa, sem endpoint novo. A execução seguirá lotes
de tarefas independentes: primeiro modelos e repositórios, depois os três
serviços + apresentadores, e por fim a documentação — fechando com `go build`
e `go test` completos.

## Implementação (2026-10-07)

A checagem entrou dentro de cada `Add`, antes do `Create` — o repositório só
responde "esse dado já existe?", a decisão fica no serviço:

- **Chave por fluxo**: contato = telefone → email → nome (o `FindByNameNorm` só
  entra quando não há telefone nem email — nesse caso a extração do nome pelo Jev
  roda antes da checagem); nota = tipo + conteúdo (+ data quando é lembrete);
  finança = tipo + valor + data (+ party só quando os dois lados têm). Os novos
  finders são `NotesRepository.FindDuplicate`, `TransactionRepository.FindDuplicate`
  e `ContactRepository.FindByNameNorm`.
- **Confirmação sem estado no servidor**: `ReceiveMessageRequest.DupAction`
  (`""` = checa, `"new"` = insere mesmo assim, `"update"` = merge no registro
  existente com o ID preservado). O `Dispatcher` devolve `outcome.Message` com a
  mensagem original, então cada superfície reenvia a mesma mensagem com o campo —
  valor desconhecido cai no `""` (checa normalmente), nunca insere às cegas.
- **WEB**: os três branches `*_duplicate` em `result.html` terminam com o
  `dup_confirm` (define irmão, pois Go template não aceita define aninhado): dois
  forms que reenviam `dup_action=update` / `dup_action=new` para `#resultado` e um
  Cancelar que limpa o card no cliente. Estilos novos no `app.css`.
- **CLI**: `render.go` imprime o bloco do duplicado e as opções `u`/`n`/`c`;
  `repl.go` guarda a mensagem pendente no Runner e só a primeira linha seguinte é
  lida como resposta — qualquer outra cancela o pendente e vira mensagem nova.
- **API**: `api.Outcome` ganhou os três cases com resumo em PT-BR no mesmo tom do
  HTML; a API só **informa** — o mesmo POST reenviado com `dup_action` faz a
  confirmação, sem endpoint novo. Swagger regenerado e `docs/` commitado.
- **Docs e testes**: ARCHITECTURE.md e CODE_STYLE.md sincronizados; testes novos
  nos repositórios, nos três serviços, no render web/CLI e no presenter
  (`go build ./...` e `go test ./...` verdes).
