# Fetching data

Agora preciso poder ver os dados que estão sendo persistidos no banco. Antes de trazer através do campo de pergunta, quero ter uma tela para poder buscar esses dados. Inicialmente quero saber quais dados atualmente estamos filtrando e persistindo. Depois vamos criar uma tela com uma aba para cada categoria que temos nas classificações. contact e notes são as que estamos persistindo, dentro de cada uma podemos ter outras subcategorias que são cada tipo de dado que salvo. Preciso disso para ir verificando o que esta sendo salvo antes de implementar e trazer pelo formulario (classificador).

## melhoria no formulário do classificador

Por enquanto o id do usuário esta mocado, então se possivel quero deixar um input hidden com esse valor e transformar o campo onde digito a mensagem em campo de texto normal, assim o enter vai funcionar para enviar a requisição.

## Comportamento dos dados

Quando eu clicar em algum botão dos dados quero poder ver em um painel lateral que se sobrepoe na lateral direita, com os dados e o botão de fechar. Isso já em formato de formulario desativado, tendo a opção de editar (habilitando os campos) e salvar as alterações.

Também quero poder selecionar mais de uma entrada daquele tipo para poder apertão um botão e apagar varios de uma vez.

## Execução

A tela de dados entra como uma feature nova, sem mexer no fluxo de classificação.
O `DataService` nasce em `internal/services/data.go` e compõe os dois
repositórios que já existem — `ContactRepository` e `NotesRepository` — em vez de
espalhar browse por `ContactService`/`NotesService`, que são do fluxo de
classificação. O `DataController` fica fino (bind → service → render) e traduz
`ErrInvalidFilter`/`ErrInvalidData` em 400 e `repository.ErrNotFound` em 404.

A navegação é 100% htmx, no mesmo formato da página `/prompts`: tabs
(Contatos/Notas) + pills de filtro, cada elemento com `hx-target`,
`hx-swap` e `hx-target-error` próprios. A tabela é um partial só
(`contacts_table` / `notes_table`) que carrega `kind`, `filter` e os checkboxes
`ids` num form escondido — é ele que o POST de delete reaproveita via
`hx-include`. O botão "Ver" troca o conteúdo de `#data-panel-body` e mostra o
offcanvas `end` na direita; o mesmo partial `data_detail` renderiza os dois
modos (`view` desabilitado, `edit` habilitado) e o POST de salvar devolve
sempre a versão `view`. Depois de salvar, o form dispara o evento `dataChanged`
no body e o container da tabela escuta (`hx-trigger="dataChanged from:body"`)
para se recarregar sozinha.

Detalhe de conteúdo: o tipo da nota é somente leitura (mudar o tipo mudaria a
semântica dos campos), a data é gravada como meia-noite UTC em `02/01/2006` e os
itens do todo são reconstruídos por completo a cada save (o `position` é
renumerado e textos em branco são descartados) — os ids dos itens mudam, o que
não afeta nada porque nada fora da tela os referencia.

Antes de criar a tela, o formulário do classificador também é ajustado: a
mensagem vira `<input type="text">` (Enter envia) e o `user_id` mockado vira
campo hidden.

## Implementação (2026-10-01)

A tela `/data` lê e edita o que os fluxos de contato e de notas já gravaram.
`DataService` compõe `ContactRepository` e `NotesRepository` direto -
`ContactService`/`NotesService` ficam de fora porque carregam a lógica de extração
do fluxo de classificação, que não significa nada numa tela de consulta. O
serviço é o único que valida filtro (`all`/`phone`/`email`/`name` e
`all`/`note`/`reminder`/`todo`); o repositório cai para `all` num filtro
desconhecido de propósito, para não repetir validação em cada chamador.

As rotas literais (`/data/table`, `/data/item-row`) entram antes de
`/data/:kind/:id`, senão o gin lê `table` como `:kind`. Visualizar e editar são o
mesmo template: o `fieldset` alterna `disabled` e os botões, sem dois ramos para
sincronizar. A linha de item de todo existe uma vez só (`data_item_row.html`),
reaproveitada com `{{ template }}` nas linhas existentes e buscada por htmx em
"Adicionar item". Nenhuma chamada ao Jev acontece nessa tela.

O filtro ativo é estado do cliente (`markFilterPill`), porque o servidor redesenha
só `#data-table` e nunca a lista de pílulas - um `active` renderizado no servidor
se perderia a cada delete. Trocar de aba externa chama `activateFilterPills`, que
carrega o filtro padrão do painel: sem guarda de `active`, já que o Bootstrap
alterna essa classe sozinho e a guarda pularia justamente o recarregamento da aba
que já está visível. O pill "Todos" de contatos usa `hx-trigger="load, click"`
para subir a tabela no primeiro paint e continuar clicável.
