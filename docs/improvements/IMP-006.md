# Migrar o front-end de Bootstrap 5.3 para Web Awesome

O front-end hoje usa Bootstrap 5.3 (CDN) + Bootstrap Icons + htmx, sem build step. O visual não é satisfactoryo e a camada de customização sobre o Bootstrap cresceu: `app.css` tem 255 linhas, boa parte delas reimplementando tokens do Bootstrap, e o `base.html` carrega um `<style>` inline. Além disso, pagamos ~320 KB de JS+CSS de CDN para um conjunto de componentes que usamos de forma rasa (card, badge, tab, offcanvas, form control).

A sugestão é trocar o Bootstrap por [Web Awesome](https://webawesome.com), a sucessora oficial do Shoelace, mantendo apenas CDN e sem build step.

## Por que Web Awesome e não Shoelace

O issue original apontava para o [Shoelace](https://github.com/shoelace-style/shoelace), mas ele foi descontinuado: o time migrou para a Font Awesome e o Shoelace está congelado na 2.20.1 (março de 2025), sem novos releases e com issues e PRs fechados.

O **Web Awesome** é a sucessora — mesmo time, mesma arquitetura de web components, prefixo trocado de `sl-` para `wa-`, e todo o catálogo de que precisamos está no plano gratuito (Core). Migrar para Shoelace hoje seria refazer o mesmo trabalho em cima de uma biblioteca congelada.

Versão alvo: **3.14.0**, via `https://ka-f.webawesome.com`.

## O que muda no carregamento

```html
<link rel="stylesheet" href="https://ka-f.webawesome.com/webawesome@3.14.0/styles/themes/default.css" />
<link rel="stylesheet" href="https://ka-f.webawesome.com/webawesome@3.14.0/styles/native.css" />
<link rel="stylesheet" href="https://ka-f.webawesome.com/webawesome@3.14.0/styles/utilities.css" />
<script type="module" src="https://ka-f.webawesome.com/webawesome@3.14.0/webawesome.loader.js"></script>
```

Saem os três `<link>` do Bootstrap, o `<script>` do `bootstrap.bundle.min.js`, o `<link>` do Bootstrap Icons e o `<link>` da fonte Inter (o tema do Web Awesome já traz a própria stack tipográfica).

## Como será executado

Cinco fases, cada uma verificada antes da seguinte e revertível isoladamente.

**Fase 1 — base.** `base.html` passa a usar `<wa-page>` com o slot `navigation` e `mobile-breakpoint="992px"`, que reproduz o comportamento de sidebar estática no desktop e gaveta no mobile. Isso substitui o `offcanvas-lg` do Bootstrap inteiro, incluindo o `@media` que precisou ser escrito à mão para consertar o comportamento no desktop. O `<style>` inline some, junto com o truque do `page:active` — o Web Awesome renderiza a navegação como marcação real, então o link ativo recebe `class="active"` direto do template.

**Fase 2 — formulários.** `.form-control`/`.form-select` viram `<wa-input>`/`<wa-select>`, `.form-check-input` vira `<wa-checkbox>` e os campos de data e hora de texto livre continuam texto livre. Os controles do Web Awesome são *form-associated custom elements*, então submetem com `name` igual a um controle nativo e o `c.ShouldBind` não muda. O `<fieldset disabled>` que trava o formulário no modo de visualização continua funcionando: o `formDisabledCallback` é chamado quando um fieldset ancestral desabilita o elemento.

**Fase 3 — tela `/data`.** As três abas viram `<wa-tab-group>` e o painel lateral vira `<wa-drawer>`. Os pills de filtro viram `<wa-button>`. O ponto delicado: `markFilterPill` e `activateFilterPills` existiam porque o servidor re-renderiza `#data-table` mas nunca a lista de pills, então um `active` renderizado no servidor se perde a cada delete.

> **Correção após a execução:** a hipótese original era que o estado do pill passaria a ser o valor do componente e o JavaScript sumiria. Isso não se confirmou — `<wa-button-group>` é puramente visual (não tem estado de seleção nem evento `wa-selection-change`). `markFilterPill`/`activateFilterPills` foram **mantidos**, atualizados para marcar `variant="brand"`/`appearance="filled"` em vez de uma classe `active`. Só a troca de aba mudou de mecânica: `onclick` por pane virou o evento `wa-tab-show` do `<wa-tab-group>`.

**Fase 4 — `result.html` e `/prompts`.** `.card` vira `<wa-card>`, as dezesseis regras `.badge-cat-*`/`.badge-kind-*`/`.badge-note-*`/`.badge-tx-*`/`.badge-match-*` do `app.css` viram o atributo `variant` do `<wa-badge>`, `.text-warning`/`.text-secondary` viram `<wa-callout>`, e o par `.htmx-indicator` + `.button-label` + `.spinner-border` vira o atributo `loading` do `<wa-button>`.

**Fase 5 — varredura e documentação.** Deletar o que sobrou no `app.css`, conferir que nenhuma classe do Bootstrap sobreviveu nos templates, e atualizar `ARCHITECTURE.md` e `CODE_STYLE.md` — este último tem regras que citam o comportamento do Bootstrap e precisam ser reescritas.

### Mapeamento de componentes

| Hoje (Bootstrap) | Web Awesome |
|---|---|
| `offcanvas-lg.sidebar` + `.app-layout` + nav mobile | `<wa-page>` slot `navigation` + `mobile-breakpoint` |
| `body.page-x` + bloco `page:active` | `class="active"` no link |
| `.card` | `<wa-card>` |
| `.badge.badge-cat-*` (16 regras CSS) | `<wa-badge variant>` |
| `.nav-tabs` + `data-bs-toggle="tab"` | `<wa-tab-group>` + evento `wa-tab-show` |
| `.nav-pills` + `markFilterPills` | `<wa-button>` + `markFilterPill` (o JS fica, ver implementação) |
| `#dataPanel` offcanvas | `<wa-drawer>` |
| `.form-control` / `.form-select` | `<wa-input>` / `<wa-select>` |
| `.form-check-input` | `<wa-checkbox>` |
| input `date`/`time` | `<wa-input>` texto livre |
| `.btn` + `.htmx-indicator` + `.button-label` | `<wa-button>` + `hx-indicator` + `<wa-spinner>` |
| `.spinner-border` | `<wa-spinner>` |
| `bi bi-*` | `<wa-icon name>` |
| `.text-warning` / `.text-danger` / `.text-secondary` | `<wa-callout variant>` |
| `.table` | `native.css` sobre `<table>` real |
| Inter (Google Fonts) | vem no tema |

### Riscos

1. **hx-swap dentro do `<wa-page>`** — é o risco principal. O conteúdo slotted continua em light DOM, então `#resultado` e `#data-table` devem continuar alcançáveis pelo htmx, mas isso precisa ser validado no navegador antes de seguir.
2. **Estado dos pills** — se a interação virar propriedade do componente, o `active` inicial que marca o filtro corrente na tela não sobrevive ao delete. É a mesma armadilha do `markFilterPill`, agora com menos código.
3. **Ícones** — catorze ícones com nomes diferentes entre Bootstrap Icons e Font Awesome.
4. **FOUCE** — nos primeiros milissegundos os `wa-*` aparecem como elementos desconhecidos sem estilo.
5. **Estado desabilitado** — `<fieldset disabled>` desabilita o controle, mas é preciso uma regra visual para o estado cinza.

### Fora de escopo

- **Dark mode.** O Web Awesome suporta nativamente e seria uma linha (`<html data-theme="dark">`), mas não foi pedido.
- **`<wa-include>`.** Substituiria o `views.PagesRenderer` por busca no cliente, mas quebraria a propriedade de renderização server-side sem build step e custaria uma requisição por página.
- **Componentes Pro.** `wa-data-grid`, `wa-date-picker` e `wa-file-input` são pagos e não são necessários — as datas aqui são texto livre em PT-BR ("10/05", "amanhã"), que é justamente o que um date picker estragaria.

## O que foi implementado

Executado em 2026-10-02. As cinco fases foram concluídas, com `go build`, `go vet`, `go test ./...` e smoke test das 10 rotas contra o servidor real.

**Arquivos trocados:** os 12 templates de `web/templates/`, mais `web/static/css/app.css`, `internal/views/render.go` (helpers `PageData` e `BadgeVariant`) e `internal/views/render_test.go`.

`app.css` caiu de 255 para 125 linhas: saíram os 16 blocos `badge-cat-*`/`badge-kind-*`/`badge-note-*`/`badge-tx-*`/`badge-match-*`, a reimplementação dos tokens do Bootstrap e o CSS morto (`.wa-badge.badge-notes`, `.wa-badge.badge-recebimento` — regras que nenhum template usava). Entraram `.htmx-indicator`, a navegação do `wa-page` e o estilo das pills.

### O que divergiu do plano

Duas premissas do plano eram falsas e foram corrigidas na execução:

1. **`<wa-button-group>` não tem estado de seleção.** Não existe evento `wa-selection-change`. O JS dos pills ficou; só a forma de marcar o estado mudou.
2. **`<wa-button loading>` não pode ser ligado pelo htmx.** O atributo é uma propriedade do componente, e o htmx alterna classes. O feedback de loading continuou sendo `hx-indicator` + `.htmx-indicator` + `<wa-spinner>`, mais `hx-disabled-elt="this"`.

### Correção pós-execução — o `app.css` estava com o vocabulário do Shoelace 2.x

O primeiro sinal foi um print da home com a sidebar "simples demais": sem o quadrado da marca e sem destaque no link ativo. Não era o Web Awesome não carregado — os quatro CDN respondiam 200 e o `wa-page`, o `wa-input` e o `wa-button` funcionavam. Quem não aplicava era a camada própria: **`app.css` foi escrito com os nomes de token do Shoelace, que o Web Awesome 3.14 renomeou**, e 16 declarações apontavam para tokens inexistentes.

Um `var(--token-inexistente)` sem fallback invalida a **declaração inteira** em computed-value time: ela calcula para `unset`/`inherit`, sem erro, sem log e sem nada no console. O sintoma é indistinguível de "o CSS não foi carregado".

Os 16 pontos mortos, e o que cada um apagava:

| Token do Shoelace (morto) | Web Awesome 3.14 | O que sumia |
|---|---|---|
| `--wa-color-brand-500` + `--wa-color-cyan-500` | `--wa-color-brand-fill-loud` + `--wa-color-cyan-50` | o degradê da marca (o `background` inteiro caía) |
| `--wa-color-brand-100` + `--wa-color-brand-800` + `--wa-font-weight-semi)` | `--wa-color-brand-fill-quiet` + `--wa-color-brand-on-quiet` + `--wa-font-weight-semibold` | **todo** o estado do link ativo — fundo, cor e peso |
| `--wa-radius-s` | `--wa-border-radius-s` | os cantos arredondados da nav |
| `--wa-color-surface-hover` | `--wa-color-surface-lowered` | o hover da nav |
| `--wa-color-success-600` | `--wa-color-success-on-normal` | o ✓ do to-do feito e o "ok" do trace |
| `--wa-color-text-muted` (3×) | `--wa-color-text-quiet` | o footer do card, o to-do feito e o ✗ do trace |
| `--wa-color-brand-700` | `--wa-color-brand-on-normal` | o destaque do total |
| `--wa-font-family-mono` (2×) | `--wa-font-family-code` | o trace de segmentos e o telefone |

Juntei a remoção de `wa-mobile-full` em `evaluation_results.html`, que também era classe do Shoelace 2.x e não existe no 3.x.

O mapeamento mecânico do degradê ficou ruim na primeira passada: `--wa-color-brand-90` é `#d1e8ff`, quase branco, então a marca virava um borrão pálido. O original (`brand-500` → `cyan-500`) eram tons médios, e o certo é o token semântico `fill-loud` (`#0071ec`), que ainda sobrevive a uma troca de hue do tema.

**Verificação.** `go build`, `go vet` e `go test ./...` passam. Além do teste novo, comparei screenshots antes/depois em Chrome headless amostrando os pixels: antes a coluna da sidebar era inteiramente branca de y=20 a y=100; depois tem o degradê (`#0276cf` → `#057bb1` em y=20/40) e o fundo do link ativo (`#e8f3ff` em y=80/100). Um diff visual da coluna inteira é mais convincente do que dizer "os tokens agora existem".

### Armadilhas que o build não pegou

Seis defeitos que só apareceram em execução ou em revisão, e que valem como regra:

1. **`data.html` definindo `data:content` em vez de `page:content`.** O `PagesRenderer` executa `page:content`; o nome errado renderizou **corpo vazio com HTTP 200**, sem log.
2. **`{{ .ID }}` num modelo que tem `PromptID`.** `html/template` escreve a saída enquanto executa, então o erro truncou o partial no meio e devolveu 200 com HTML pela metade.
3. **`data_item_row.html` nunca migrado** (continuava em `btn`/`form-control`/`bi-trash`) e o teste passava porque nenhuma asserção cobria as classes. A varredura de texto achou; o teste foi reforçado para cobrir `wa-input`/`wa-checkbox`/`wa-icon` e o `item_done` oculto.
4. **`<wa-checkbox name="item_done">` desmarcado não envia nada.** `DataService.buildItems` lê `dones[i]` posicionalmente contra `texts[i]`, então sem o input oculto sincronizado os arrays desalinhariam e a linha errada seria marcada como feita. O `onchange` que escreve no input oculto foi preservado — e verificado com um POST real (`0,1,0` → inalterado, marcado, inalterado).
5. **CSS e template dessincronizados.** `.htmx-indicator`, `.sidebar-nav` e a classe de texto da linha de to-do (`todo-text` no template, `todo-item-text` no CSS) estavam com nomes que não cruzavam. Nenhum desses era coberto por asserção de teste.
6. **`app.css` inteiro no vocabulário de token do Shoelace 2.x** — a correção acima.

**A lição comum dos seis:** todos produzem HTTP 200, saída vazia ou estilo ausente, e nenhum é coberto por asserção. A defesa é cruzar o que você escreve com o que a biblioteca realmente exporta, num teste — foi o que a varredura de classes e o teste de token fizeram aqui.

### Verificação

`go build ./...`, `go vet ./...` e `go test ./...` passam. Smoke test das 10 rotas contra o servidor real: 200 nas nove esperadas, 404 nos registros inexistentes e 400 no `kind` inválido (`/data/note/1` — o valor correto é `notes`), ambos os comportamentos corretos. O `POST /api/message` rodou o fluxo Jev de verdade e renderizou o card de resultado. O round-trip monetário foi conferido ponta a ponta: o campo vem preenchido com `R$ 10,00` e volta para `10.00` no banco, não `1000`.

`ARCHITECTURE.md` e `CODE_STYLE.md` foram atualizados (a seção `### Frontend (Web Awesome)` do `CODE_STYLE.md` é nova). Os documentos históricos (`DC-*`, `IMP-002` a `IMP-005`) ficaram como registro do que era verdade na época.
