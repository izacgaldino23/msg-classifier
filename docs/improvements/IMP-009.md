# Diagramas de fluxo

Como o fluxo depende muito do que o usuário escreve fico um pouco perdido no que ja fizemos até agora na parte de cli principalmente. Mas acho que o de fluxo vai valer para o cli e o web, se não podemos separar.

Com esse diagrama quero ter certeza o limite do que pode ser solicitado pelo usuário, falando da parte de msg. Mas também quero ter uma visão da parte de dados, do que pode ser feito lá. No cli não sei se dá para ver isso.

Pra esse diagrama gostaria de fazer usando PlantUML. Vou usar a extensão para visualização no vscode. Mas também tem o site para visualizar, nao quero que seja gerado imagem nenhuma somente os diagramas, assim, se precisar de alguma alteração eu mesmo pedirei.

Como nosso sistema está em pleno crescimento é desejavel que seja adicionado no CLAUDE.md uma ordem para que se algo for modificado no fluxo, seja adicionado no diagrama de fluxo. Assim, podemos ter uma visão geral do que o bot pode fazer e como ele funciona.

## Resultado (implementado em 2026-10-09)

Quatro diagramas em PlantUML, **só o fonte** — nenhuma imagem é gerada ou commitada (você abre com a extensão PlantUML no VS Code ou cola em <https://www.plantuml.com/plantuml>):

| Arquivo | Tipo | O que mostra |
|---|---|---|
| `docs/diagrams/visao-geral.puml` | componente | os três entrypoints (web · api · cli) sobre o `internal/app`, os serviços, os repositórios, o SQLite e a Jev. |
| `docs/diagrams/fluxo-mensagem.puml` | atividade | o limite de uma mensagem: classificação (1 chamada Jev) → categoria → `contact`/`notes`/`finance` em add × require, com cada action de saída, e `schedule`/`other` caindo em `ActionNone`. |
| `docs/diagrams/fluxo-dados.puml` | atividade | a tela `/data`: filtro, busca, Ver, Editar, item de tarefa e apagar. |
| `docs/diagrams/fluxo-cli.puml` | atividade | o REPL: cada linha vira comando (com os filtros de cada listagem) ou mensagem, com o `u`/`n`/`c` pendente. |

Duas respostas ao que ficou em aberto no texto acima:

- **cli × web: não precisou separar.** O fluxo de mensagem é o mesmo core nos três entrypoints (web, api e cli); o que muda é só como a resposta é apresentada, e isso ficou no `fluxo-cli.puml`. Por isso o fluxo de mensagem é um diagrama só.
- **Dá para ver os dados no cli?** Em parte: `/contatos`, `/notas` e `/financas` listam pelo mesmo `DataService` (anotado no `fluxo-dados.puml`), mas só a tela `/data` escreve — o CLI não edita nem apaga.

A regra de manutenção entrou no `CLAUDE.md` (seção **Diagramas de fluxo**): mudou o fluxo — categoria, action, rota, comando, filtro, tela — o diagrama correspondente muda na mesma alteração.

### Esboço (trecho do fluxo-mensagem)

```
start
:Classify — 1ª chamada Jev (categoria + add/require);
switch (categoria?)
case (contact)
  if (require?) then (sim)
    :busca em ordem: telefone → e-mail → nome (LIKE em name_norm);
  else (add / both)
    :regex telefone/e-mail | 2ª chamada Jev para o nome;
    :checa duplicado;
    :contact_duplicate | contact_add | contact_no_data;
  endif
case (schedule · other)
  :ActionNone — a categoria é reconhecida, sem caso de uso;
endswitch
:o presenter mostra o resultado;
stop
```

Verificação: os quatro passam `plantuml.jar -checkonly` e renderizam (SVG gerado fora do repo, só para conferir). O conteúdo foi conferido contra o código: as 16 actions de `internal/models/message.go`, os seis comandos do `commandTable()`, os mapas de filtro do CLI e as rotas do web e da API.
